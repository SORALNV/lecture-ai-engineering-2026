# 第4回 解答

## 演習

今回は宿題の発展課題を実施しました。講義内の10件への人手ラベル付けとLLM採点の比較実験は実施していません。

## 宿題

- 取り組んだレベル：発展
- やったこと：SWE-bench Verifiedを選び、実際の課題例、作成・検証方法、採点方法を公式資料で調べ、第4回の評価セットと比較しました。

### ベンチマークの概要

[SWE-bench Verified](https://huggingface.co/datasets/SWE-bench/SWE-bench_Verified)は、公開Pythonリポジトリで報告された実際のソフトウェア課題を、AIエージェントが修正できるか測るベンチマークです。エージェントには修正前のコードとGitHub issueの説明が渡され、修正後のテストは見えません。課題の説明だけでなく、コードを読み、修正し、テストで既存機能を壊していないことまで確かめる必要があります。[公式紹介](https://openai.com/index/introducing-swe-bench-verified/)

### 読んだ課題例

以下は、SWE-bench Verifiedの作成者による公式紹介・監査記事に掲載された課題例を読み、全文を転載せずに要約したものです。

| 課題例 | 何を問うか | 自力で解く見通し・LLMにとっての難しさ |
|---|---|---|
| [`pylint-dev__pylint-4551`](https://github.com/pylint-dev/pylint/pull/4551) | Pythonの型ヒントをUML図の生成に反映する機能を扱う。 | 自力なら再現例を作り、図の出力経路と型情報の扱いを追えば実装できそうです。ただし、要求文で説明されない内部APIを評価テストが前提にしている場合、仕様から自然に導ける実装と採点上の期待がずれるおそれがあります。LLMにも、既存設計の理解とテスト適合の両立が課題です。 |
| [`sympy__sympy-18199`](https://github.com/sympy/sympy/pull/18199) | `nthroot_mod`が、`a ≡ 0 (mod p)`のとき根`x ≡ 0 (mod p)`を返さない問題。 | 自力なら小さな具体例を作り、合同式を計算して欠けた根を確認できます。一方、このPRは別の2件の関連issueも同時に直しており、評価用の問題文はそのうち最後の1件しか説明していません。LLMが問題文に書かれた修正を正しく行っても、他の2件に対応するテストまで通らなければ失敗扱いになる点が難所です。 |
| [`django__django-11451`](https://github.com/django/django/pull/11451) | 認証情報が欠けている場合に、認証処理が不要なデータベース検索を行わないようにする課題。 | 自力では認証フローとユーザー名の代替処理を読んで、不要な検索だけを防ぎつつ既存動作を保てるか検証する必要があります。LLMも、単純な条件分岐に見える変更で副作用を起こさないこと、また公開済みの修正を記憶している可能性と実際の推論を区別しにくいことが難点です。 |
| [`astropy__astropy-13236`](https://github.com/astropy/astropy/pull/13236) | 構造化NumPy配列を`NdarrayMixin`へ自動変換する既存挙動を段階的に止める課題。まず`FutureWarning`で明示的に`Column`で包むよう案内し、5.2で自動変換を取り除く移行が求められます。 | 自力では利用者への影響を考え、警告の開始と挙動変更の時期を一貫させる必要があります。LLMは、公開された修正内容を記憶していないかを独立に確かめるのが難しく、この例は実際にモデルがPRのコード詳細を再現した汚染の例としても紹介されました。 |

現時点では、4件ともissueの要望を読み解き、調査方針を立てることはできます。一方、初見で安全に修正を完成させられるかは、リポジトリの設計とテストを確認しないと判断できません。上表では「今の自分が着手できるか」と「LLMの評価で難しさになる点」を課題ごとに分けました。

### 作成・検証の方法

元のSWE-benchは、12のオープンソースPythonリポジトリから、解決済みissueと対応する修正PRを組にして作られています。OpenAIは作成者と協力し、Python開発経験のある93人の開発者が、抽出した1,699件についてissueの説明やテストの妥当性を確認しました。各候補を3人が独立に評価し、紹介記事では68.3%を問題文・テストなどの懸念から除外したと報告しています。500件は単純に残りを全採用したのではなく、少なくとも1時間程度の作業が見込まれる課題を優先し、残りから抽出して構成されました。[作成・フィルタリングの説明](https://openai.com/index/introducing-swe-bench-verified/)

### 採点方法

各課題には、修正前には失敗し、正しく直すと成功する`FAIL_TO_PASS`テストと、修正前後とも成功すべき回帰テスト`PASS_TO_PASS`があります。エージェントにはテストを見せず、提出したコード変更をコンテナ環境で実行します。課題を解決したと数えるには、失敗から成功へ変わるべきテストと、既存機能を守るテストの双方に通る必要があります。集計は通常、解決できた課題の割合（resolved rate）です。[公式評価方法](https://openai.com/index/introducing-swe-bench-verified/)

### 第4回の評価セットとの違い

第4回では、講師が第3回のエージェントを使って生成した質問・回答10件を題材にします。「根拠・範囲・ヒント・分かりやすさ」の4基準は人手ラベルとLLM判定を比較し、「回の表示」はコードで判定します。人とLLMの基準別一致率や`unsure`を見て、評価基準を改善する演習です。一方、SWE-bench Verifiedは500件の実リポジトリ修正課題を、隠した実行テストで判定します。前者は小さな教育用評価セットで評価器の判断を点検し、後者は複数リポジトリにまたがる実装課題で修正の正しさと回帰の有無を測る点が異なります。

### 限界と今回の調査で分かったこと

人手で検証したことは品質を高めますが、ベンチマークを完全に正解にするわけではありません。2026年2月のOpenAIによる再監査では、モデルが安定して解けなかった138件を各6人以上の経験ある開発者が確認し、その59.4%に、機能的に正しい修正を落とすテストや説明との不一致など重大な問題があったと報告されています。また、公開リポジトリ由来のため、学習データへの混入を完全には防げず、モデルが元の修正を再現できた事例も報告されました。これは失敗した138件の監査結果であって、500件全体の不具合率と同じではありません。OpenAIはこの理由からVerifiedのスコア報告を停止すると表明しています。[2026年の再監査と制約](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/)

この調査から、ベンチマークの数値はモデル能力だけでなく、問題文、テスト、実行環境、学習データとの重複にも左右されると分かりました。高い一致率や解決率を見るだけでなく、どの例を何人が確認し、何を正解と定義したかを読むことが評価の前提だと感じました。
